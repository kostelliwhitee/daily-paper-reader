## 摘要
多智能体氛围编码（vibe coding）有望加速软件开发，然而现有基准依赖于忽略实际时间和货币成本的合成环境，将推理与通信混为一谈，并且仅奖励表面化的完成。我们引入了多智能体从零开始评估基准MSEval，在真实世界任务上评估多智能体编码。基于跨10个领域的10个真实全栈项目，MSEval使用分层需求和确定性评分标准对性能进行评分。其执行引擎LegoGent测试了10种协作拓扑，其中智能体通过周期性同步间隔进行协调，并通过原生CI/CD管道进行部署。同时，自动评分器TAgent动态探测实现，以联合衡量功能成功、延迟和前缀缓存令牌成本。在100次运行中，MSEval揭示了组织拓扑在塑造速度-成本-质量权衡方面可与模型能力相媲美。对于相同的任务和模型，改变拓扑可使得分发生超过30分的偏移，并使墙钟时间加倍。结构化管道以最高质量最快收敛，而繁重的管理监督则会降低性能。最终，MSEval建立了衡量多智能体团队实际构建软件的严谨、可复现标准。该基准已在https://github.com/robinren03/MSEval发布。

## Abstract
Multi-agent vibe coding promises to accelerate software development, yet existing benchmarks rely on synthetic environments that ignore practical time and monetary costs, conflate reasoning with communication, and reward only superficial completion. We introduce multi-agent from-scratch evaluation benchmark, MSEval, evaluating multi-agent coding on real-world tasks. Grounded in 10 authentic, full-stack projects across 10 domains, MSEval scores performance using hierarchical requirements and deterministic rubrics.   Its execution engine, LegoGent, tests 10 collaboration topologies where agents coordinate via periodic sync intervals and deploy through native CI/CD pipelines. Concurrently, the automated grader TAgent dynamically probes implementations to jointly measure functional success, latency, and prefix-cached token cost. Across 100 runs, MSEval reveals that organizational topology rivals model capability in shaping the speed--cost--quality trade-off. For identical tasks and models, varying the topology shifts scores by over 30 points and doubles wall-clock time. Structured pipelines converge fastest with the highest quality, whereas heavy managerial oversight degrades performance. Ultimately, MSEval establishes a rigorous, reproducible standard for measuring how multi-agent teams actually build software. The benchmark is released at https://github.com/robinren03/MSEval.

- **研究背景**：前沿编码智能体已能进行仓库级编程，但现有评测仍聚焦于单智能体生成补丁或修复缺陷，无法回答实际开发中更关键的问题：一组智能体如何分工、从零构建全栈项目、花费多少时间与令牌、并在具体反馈下改进。
- **核心问题**：现有基准确认缺失了“协调模式”这一变量——它们要么使用合成环境，忽略实际时间和货币成本；要么将推理与通信混为一谈；要么只以最终文本/补丁质量评分，而不关注可运行的软件交付。
- **整体含义**：论文提出 MSEval 基准，首次将“多智能体协作拓扑”作为一等公民来评估从零编码。其关键论断是：组织拓扑（如何划分工作、谁拥有什么、如何合并）与模型能力同样决定了速度-成本-质量权衡。

## 2. 方法论

- **总体框架**：MSEval 是一个三阶段流水线：
  1. **数据基础**：从大学软件工程课程中筛选 10 个真实全栈项目，每个项目有分层需求文档，细分为 30–45 个加权检查项，归一化为 100 分制评分标准。
  2. **执行**：LegoGent 运行时实例化协作模式，启动智能体，监控进度，并将生成的代码库交给 XDeploy 通过 GitLab + SonarQube 进行原生 CI/CD 部署。
  3. **评估**：TAgent 自动评分器对部署产物进行 UI、API、代码多维度探测，返回加权完成分数和时间、令牌成本；反馈进入下一轮修复，最多三轮。

- **LegoGent 执行引擎**：
  - 每个智能体作为隔离、可恢复的进程运行，拥有文件与 shell 工具。
  - **有界同步机制**：
    - 被动同步：每约 4 分钟广播一次团队进度快照（每个智能体报告完成工作、测试证据、阻塞点、下一步）。
    - 主动信箱：支持智能体间定向提问和交接。
    - 完成门：要求所有智能体空闲且所需产物齐备，才进入部署与评估。
  - **实现 10 种协作模式**，每个模式由四个对象定义：所有权映射、激活计划、决策规则、必需交接产物。

- **TAgent 自动评估器**：
  - 解析需求文档为结构化 YAML 评分标准，每个检查项具有权重和通过/部分/失败判定。
  - 三类评估器：
    1. **UI**：Playwright 驱动真实浏览器，读取可访问性树/DOM，判断页面状态。
    2. **API**：从 OpenAPI 或源码重构路由，执行带身份验证的 HTTP 序列。
    3. **代码**：目录过滤 + 定向搜索 + LLM 检查不可见约束（如密码哈希、CI/CD 配置）。
  - **依赖感知的并行调度**：用 LLM 声明 UI 检查的阻塞依赖，构建 DAG，用整数规划将任务划分到浏览器工作线程，最小化 makespan 和重复设置；支持前置条件级联跳过、重复抽查合并。
  - 输出条目级证据（观察到的状态、API 响应、代码位置、受影响的权重），形成排名修复议程。

- **成本度量**：记录每智能体每轮的新输入、缓存创建、缓存读取、输出令牌，并按提供商单价加权计算美元成本。

- **关键设计决策**：在固定项目、模型、部署路径和评分标准下，唯一改变的是协作拓扑，从而使拓扑的影响可测量且可归因。

## 3. 实验设计

- **任务与基准**：
  - 10 个真实全栈 Web 项目，涵盖即时通讯、企业资产、众包、需求跟踪、AI 图像恢复、电商、创作者分析、权限平台、新闻搜索、在线直播教学。
  - 难度分布：最难的为在线直播教学（平均 67.1 分）和 AI 图像恢复（69.1 分），最易的为新闻搜索（92.8 分）、权限平台（91.0 分）、影响力分析（90.5 分）。
  - 每个项目编译为 100 分制加权评分标准（例如 IM 项目 56 个检查项：7 系统 + 46 功能 + 3 文档）。

- **协作模式组合**：
  - 10 种模式分为两类：
    - **串行交接型**：Feature squad、Layer specialists、Pipeline、QA-first、Rotation。
    - **并行竞争型**：PM oversight、Swarming、Open-source review、Adversarial、Competitive。
  - Pipeline 模式故意几乎串行，作为协调控制条件。

- **模型**：
  - 全网格模型（运行全部 10 个项目）：DeepSeek v4 Flash、DeepSeek v4 Pro、GLM-5.2。
  - 仅在 IM 项目（P00）运行的模型：Claude Opus 4.8、GPT-5.5、Qwen3.6-Flash（因全模式得 0 分而弃用）。

- **对比方法**：没有传统基线模型对比，而是对同一模型在不同协作模式下的表现进行系统比较；与现有基准（SWE-bench、MultiAgentBench、CloudDevBench、DeepSWE、FrontierCode、TheAgentCompany）在特性表（表 1）中定性对比。

- **评估流程**：每配置最多三轮细化；每轮构建/修补 → 部署 → TAgent 评分 → 反馈进入下一轮；记录最佳轮次的完成分数、分钟、美元成本、总令牌数。

- **验证**：在 3 个 IM 项目配置上运行 3 个平行试验，其他项目在异常时重跑；TAgent 分数与学生 TA 评分的 Spearman 相关为 0.87。

## 6. 主要结论与发现

- **拓扑效应显著**：
  - 在 IM 项目中，同一模型（DeepSeek v4 Pro）在 pipeline 模式下得 89.9，在 open-source review 下仅 43.0。
  - 全网格平均：QA-first 和 Rotation 并列最高（83.3），Open-source review 最差（73.5）；模式范围仅约 10 分，但在单个项目内差异极大（如需求跟踪 57.2–91.7）。
  - 结构化、有明确产物边界的模式（pipeline、feature squad、QA-first）收敛快、质量高；管理监督过重（PM oversight）或权限分散（open-source review、adversarial）会导致性能下降。

- **反馈驱动改进有效**：
  - 82.0% 的相邻轮次转换得分提高，94.7% 的运行第三轮高于第一轮。
  - 三轮后增益边际递减（73.3% 的 R2→R3 增益 <20 分），因此三轮预算合理。

- **性能天花板源于功能缺陷而非崩溃**：
  - 1,440 个失败检查项中，约 56% 属于“不完整逻辑/边界情况”（32.2%）和“缺失功能”（23.8%）。
  - 认证/权限（11.9%）和前置条件级联（11.0%）合计 23%；一个坏前置条件可自动跳过最多 14 个下游检查，这是多智能体特有的“契约破坏”问题。
  - 安全与传输项（8.5%）在近 80% 的运行中出现，源于部署层集成失败而非纯代码错误。

- **成本前沿与得分前沿不同**：
  - GLM-5.2 取得最高全网格平均分但耗时约为 DeepSeek v4 Pro 的 2.6 倍、成本约 8 倍；GPT-5.5 以远低于 Claude 的成本达到几乎相同的 IM 得分。
  - 令牌总量大不等于美元成本高：缓存读写价格差异极大，必须按字段计价。

- **协调政策是可操作的控制面**：并行化仅在反馈仍可映射到明确责任人时才有效，否则需求失败会变成“谁的改动被保留”的谈判；模式特征波形（雷达图）揭示了低分-低耗时（早期部署失败）和高令牌-中分（重复返工/修复错误层）等不同失败签名。

## 7. 优点

- **填补空白**：首次将“从零开始多智能体编码 + 多协作模式 + 部署验证 + 成本度量 + 多轮反馈”组合在同一基准中，与现有基准形成明确区分。
- **真实性与可控性**：使用真实课程项目需求文档（无预定义 API 细节），同时保持项目、模型、评分标准固定，仅改变协作拓扑，使得拓扑效应可归因。
- **部署而非文本评估**：通过 CI/CD 部署到独立端口，用真实 UI/API/代码检查评分，避免自报完成的虚假成功。
- **自动、可复现的评估器**：TAgent 不依赖预定义测试或人工裁判，而是动态发现路由和表面，输出条目级证据；与学生 TA 评分相关性 0.87，验证了有效性。
- **成本与速度作为一等指标**：同时报告分数、分钟、美元、令牌，支持帕累托前沿分析，而非单一分数排行榜。
- **丰富的模式定义**：10 种模式以统一模板（所有权、激活、决策、交接产物）定义，可清晰对比串行交接与并行竞争的成本。
- **反思性局限讨论**：坦然承认随机性、项目范围、生命周期覆盖等不足，增强了可信度。

## 8. 不足与局限

- **随机性与可重复性**：受高测试预算限制，仅 IM 项目做了 3 次平行重复，其他项目未重复，LLM 随机性可能影响部分结论。
- **任务范围受限**：所有项目均为 Web 应用，未覆盖命令行工具、算法库、嵌入式等非 Web 领域；TAgent 可能遗漏某些边缘缺陷。
- **模型覆盖不均**：全网格仅 3 个模型，2 个模型只测 1 个项目，Qwen 因全 0 分被丢弃，限制了模型能力维度的普适性。
- **生命周期覆盖有限**：只关注编码阶段的协作、迭代与成本，未覆盖事件响应、长期维护、生产运维等软件生命周期其他环节。
- **固定轮次可能截断收益**：90 分钟轮次预算会截断 GLM-5.2 等慢速模型的首轮实现，导致早期分数偏低；虽主要影响早期轮次，但可能使某些模式的排名失真。
- **部署层带来的固定扣分**：安全与传输检查（如 TLS、HTTPS 重定向）依赖 XDeploy 集成，近 80% 运行中出现固定扣分，这部分不是编码错误的反映，而是评估基础设施的常数偏差。
- **版本与引用风险**：论文引用的模型（Claude Opus 4.8、GPT-5.5、DeepSeek-V4、GLM-5.2）和 arXiv 日期为未来时间，可能存在前瞻或虚构因素，实际复现性需以最终发布版本为准。
