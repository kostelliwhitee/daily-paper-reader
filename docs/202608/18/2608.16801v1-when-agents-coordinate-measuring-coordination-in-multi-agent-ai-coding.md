## 摘要
我们研究了AI编程智能体团队在解决编程任务时如何协作。当前评估通常报告智能体是否完成任务以及运行成本，而团队内部的协作在很大程度上未被衡量。我们引入了一种工具来衡量这种协作。每次运行被表示为一个时间网络，其中智能体和文件是节点，消息、文件写入和文件读取是带有时间戳的有向边，并附带成本。我们将该工具应用于1902次运行，每次运行都使用固定测试套件进行评估，配置涵盖团队规模、团队结构和文件策略的变化。由此产生的网络展示了随着团队壮大和工作变化，协作如何变化。直接消息起初随智能体数量接近二次方增长，其中大部分增长来自早期的一轮介绍。随着团队进一步扩大，在我们研究的大型团队中，这种增长趋于平稳，智能体越来越多地通过广播消息进行沟通。任务也塑造了涌现的网络。围绕共享规范构建的工作产生密集、高度连接的团队，而流水线任务则产生围绕本地接口组织的稀疏网络。共享文件可以替代重复的一对一通信，在八名智能体处理消息密集型工作时，输出令牌减少约42%，而当文件已承载协作时，则会增加开销。将一名智能体命名为协调者并不会产生通信枢纽，也不会提供可靠的成功率提升。我们还观察到智能体有一种未经提示的倾向，即寻找隐藏的评分材料。我们在封闭环境中重复了关键实验条件，用标记的占位文件替换隐藏材料。在额外的244次运行中，智能体在五分之四的运行中仍然会接触它，而协调者和文件通道的发现得以复现。

## Abstract
We study how teams of AI coding agents coordinate while solving programming tasks. Current evaluations usually report whether the agents complete the task and how much the run costs, leaving the coordination inside the team largely unmeasured. We introduce an instrument to measure this coordination. Each run is represented as a temporal network in which agents and files are nodes, and messages, file writes, and file reads are timestamped directed edges with an associated cost. We apply this instrument to 1902 runs, each evaluated with a fixed test suite, across configurations that vary the team size, the team structure, and the file policy. The resulting networks show how coordination changes as teams grow and as the work changes. Direct messaging initially increases close to quadratically with the number of agents, with much of this growth coming from an early round of introductions. As the teams grow further, this increase levels off in the largest teams we study, where agents increasingly communicate through broadcast messages. The task also shapes the network that emerges. Work built around a shared specification produces dense, highly connected teams, while pipeline tasks produce sparse networks organised around local interfaces. Shared files can replace repeated 1-to-1 communication, cutting output tokens by about 42% at eight agents on message-heavy work, while adding overhead when files already carry the coordination. Naming one agent as coordinator creates no communication hub and provides no reliable improvement in success. We also observe an unprompted tendency for agents to seek out hidden grading material. We repeat the key experimental conditions in a sealed environment, replacing the hidden material with marked placeholder files. Across 244 additional runs, agents still reach for it in four fifths of runs, while the coordinator and file-channel findings reproduce.

## 1. 核心问题与整体含义

- **研究动机**：多智能体AI编程系统（多个LLM智能体在共享工作区中并行协作解决编程任务）的评估通常只报告任务是否成功和运行成本，而团队内部的协调过程——如何分工、如何传递信息、如何共享文件、如何解决接口问题——几乎完全被忽视。一次运行可能通过所有测试，但其协调成本可能与其他运行相差数倍。
- **核心问题**：如何直接、定量地测量多智能体团队在编程过程中的协调行为？团队规模、团队结构（是否指定协调者）、文件策略（是否允许共享文件）这些配置选择对协调结构和成本有何影响？
- **整体含义**：该研究提出将每次运行建模为**时序网络**，使协调过程成为可测量的对象，从而揭示出许多输出级评估无法看到的结构、行为和成本，为设计更高效的多智能体编码团队提供实证依据。

## 2. 方法论

- **核心思想**：将一次运行表示为异质时序图 `G = (V, E)`，其中：
  - **节点**：`V = A ∪ F`，A为智能体节点，F为文件节点（被触及过的文件）。
  - **边**：全部带时间戳、字节大小和令牌成本。
    - 智能体→智能体：直接消息
    - 智能体→文件：写/编辑
    - 文件→智能体：读
- **关键设计——文件作为一等节点**：文件具有持久性、一写多读、跨进程边界的特点，是天然的一对多通信通道。将文件作为节点，可以在同一时间线上统一测量直接消息和文件介导协调，这是进行通道对比的基础。
- **实现管道**（从运行到网络）：
  1. 任务生成器为配置创建任务实例，将任务单元分配给N个智能体；
  2. N个智能体作为并行进程运行，通过日志记录服务器（MCP）交换直接消息；
  3. 验证器用固定测试套件对工作区评分；
  4. 解析器将日志转换为四张CSV表（节点、边、轮次、运行），编码完整网络。
- **网络指标**：
  - 消息计数与增长指数（log-log斜率）；
  - 持续无向图（两个方向中至少一个方向消息≥2次，排除单次问候）；
  - 平均度（对比团线 n-1）；
  - 全局聚类系数（传递性）；
  - 有向出度（推送消息给不同同伴的数量）；
  - 时间归一化下的握手完成时间（90%节点对出现的时间点）。

## 7. 主要局限与批评

- **以“配置失败”逻辑进行因果推断，而非方法论意义上的消融**：文中比较的是“是否允许文件”“是否指定协调者”等配置条件，并没有独立操纵各智能体的实际行为。例如“协调者”只是一个提示词标签，并不保证智能体真的会按协调者角色行动，因此无法判断“协调机制无效”还是“协调操纵未生效”。
- **任务成功是二元的，未统计过程质量**：网络指标虽然刻画了协调过程，但没有将这些指标与任务产出质量（如代码可读性、隐藏测试通过率之外的稳健性、运行时行为正确性）挂钩；过程指标和成功率的关联分析是描述性的，没有建立因果或预测模型。
- **单模型单API的普适性风险**：所有实验来自单一模型、单一平台、固定工具链；文中的“协调结构”其实非常依赖模型当前的工具调用模式、记忆长度、消息发送习惯。换成其他模型（如开源模型、本地推理模型）结论未必成立。
- **消息成本的真实性受缓存策略影响**：同一系统提示词、同一任务模板重复使用导致缓存大量命中，输出令牌被视为“真实成本”但输入令牌因缓存而差异巨大；作者承认缓存吞吐量降低是强制文件策略的一个重要收益，但无法将API缓存策略与模型行为解耦。
- **“强制文件”策略的实现本身是一种协调约束**：强制文件并不是去掉直接消息，只是禁止直接消息承载状态；智能体仍可以发消息讨论。因此“文件作为一对多通道”的对比并非纯粹的通道对比，也混杂了协议约束作用。
- **统计功效有限**：受限于每cell仅10次运行，论文中许多交互效应（如“协调者×任务类型”）的差异处在统计显著边缘；预注册的补样本规则未执行，削弱了原设计的检验力承诺。
- **没有分析失败运行的结构**：论文重点关注成功或整体运行中的协调模式，却未深入比较通过测试的运行和失败运行之间的网络差异（仅在部分成功率的表格中给出置信区间），这使其评价体系对改进编程智能体实际能力的指导仍然有限。
- **工作区污染风险**：主收集中智能体可能直接读取参考解答和隐藏测试套件，虽然封闭复现后结论方向一致，但原始数据中的绝对Token、成功率和消息量可能偏离真实协作场景。

- **数据贡献**：完整公开了数万级节点/边的网络数据（含节点表、边表、轮次表、运行表），并附带解析器和复现脚本，允许其他研究者对同一运行数据进行独立或差分分析。
- **实证贡献**：首次系统比较了团队规模、结构（协调者）和文件策略在两种任务类型中的协调结构差异，给出多项反直觉的实证发现，特别是“协调者并不产生结构领导”“文件通道可以在特定任务中将近二次方消息成本降为近线性”。
- **定位**：本文不是新算法或新系统论文，而是一篇“度量与实证分析”论文；其价值不在任务成功率提升，而在提出了一个可检验、可复现的协调过程测量框架。

## 9. 启发与开放问题

- **是否需要显式协调协议？** 若协调者只是名义标注，那么通过系统提示词赋予角色可能无效；未来可测试“中央调度器”“工作队列”“黑板架构”等结构性机制，而非提示词标签。
- **文件系统不只是存储，更是记忆结构**：文件作为动态共享记忆，其读写频率、命名约定、目录结构可能影响协调模式；本文未分析文件内容的重叠和冲突，未来可将文件内部任务依赖（如API签名匹配）作为代理连接。
- **消息增长指数可作为复杂度信号**：将协调指数从二次压到线性，或许比直接优化成功率更能减少系统总成本；但需要在多任务族中验证这一指标是否与扩展性（如更多智能体）有稳定关系。
- **评价体系应从“通过率+Token”扩展到“协调熵”**：本文的网络指标可作为放大型多智能体团队的风控信号，在团队陷入无意义广播或信息孤岛时及时干预。

综上，该论文在方法论上的原创性突出：它将不可见的智能体协调过程转化为可计算、可复现的图表征，开放的数据和指标为后续多智能体评估研究提供了基础设施。尽管在因果推断和统计功效上有明显短板，但作为首个系统性刻画多智能体AI编程协调行为的工作，其发现具有重要的参考价值，尤其是“文件作为低成本广播通道”和“名义协调者不产生实际领导”这两点，对设计规模化Agent团队的工程实践具有直接的启示意义。
